### App 1.0.0.30 physical CPU cache result

The app 1.0.0.30 probe located the actual five-layer Q4_0 SWA cache inside
`llama_kv_cache_iswa` and compared its packed rows to the GPU cache. For
11 recorded positions, **all five K layers matched exactly**, each with
7,040/7,040 bytes. The V layers differed by 919, 784, 753, 897, and 1,060
bytes respectively, each out of 7,040. The cache has capacity 49,152
positions and an SWA window of 2,048; the window is not the capacity.

GPU SYNC still used original F32 activations for Q4_K/Q5_K WV projections,
while GGML quantizes those activations to Q8_K. The Q3_K WK path already
uses Q8_K and produced bit-identical K cache bytes. Therefore WV activation
semantics is the next correction to test. App 1.0.0.30 DRAFT still failed:
first-block `kqv_out` max absolute error 1.2684 and batch-5 final hidden
max absolute error 2.6503. The attention shader's Q8_0 FP16 rounding fix
alone did not change those values. These measurements are in
`sync-11-1.0.0.30.json` and `draft-1.0.0.30.json`.

## Location of the SYNC mismatch

App 1.0.0.23 compared intermediate values on the Xbox:

- Raw FC CPU GGML versus GPU: 54,863/56,320 values outside tolerance; maximum
  absolute difference 45.307617. First value: CPU 47.9673729, GPU 49.4648285.
- `llama_decode` encoder versus CPU RMSNorm of the CPU FC: 56,320/56,320
  bit-exact.
- GPU encoder versus CPU RMSNorm of the GPU FC: 56,320/56,320 within tolerance;
  maximum absolute difference 9.536743e-7.

Thus the observed encoder mismatch originates in FC. GGML's Q3_K CPU matmul
quantizes F32 activation rows to Q8_K before the dot product, while the tested
HLSL Q3_K kernel used the original F32 activations. The kernel previously
compared against dequantized weights times F32 activations; that validated the
different arithmetic, not CPU GGML parity. A Q3_K × Q8_K path is being
implemented and must pass host and Xbox parity before GPU SYNC can be enabled.
Q4_K/Q5_K draft projections also need this activation-semantics check.

### F4 root cause: quantization-boundary sensitivity, faithful kernels

The `draft-1.0.0.41.json` probe emitted raw CPU and GPU values for
`ffn_norm-1` and `ffn_conv_coeff-1`. Reproducing both sides on the host with
the real `blk.1.ffn_conv_proj` Q3_K weights (`t.blk_1_ffn_conv_proj_weight.bin`,
2,816,000 bytes) showed:

- Q8_K quantization flips between CPU and GPU inputs: **0 (row 0) and 1
  (row 1)** of 5,120 values; 16/15 scale fields differ by up to 4e-9.
- Each side's captured coeff matches its own replicated Q8 dot to rms 7-8e-8
  (the F32 accumulation noise floor).
- The actual CPU-GPU coeff delta (rms 2.57e-5, max 1.19e-4) is predicted by
  the replicated delta with **correlation 0.999991** and residual rms 1.07e-7.

So the GPU kernels, quantizer and dot products are faithful; the layer-1 FFN
divergence is a single Q8_K quantization-bin flip caused by the ~1e-6 F32
difference in `ffn_norm-1`, amplified ~667x by the FFN block and further by
later layers. Switching the DRAFT/SYNC engines to the FP64 `QuantizeExact`
variant did not change the result (1.0.0.40), confirming that ULP-level
divide differences are not the driver; the input delta is. Bit-identical
CPU/GPU activations are not achievable across different reduction orders, so
DRAFT hidden-state parity cannot reach bit level; the plan's F0 note already
forbids imposing binary identity on different reduction orders.

### F5: GPU executor integrated into the RPC (app 1.0.0.42)

`LocalState\dflash-backend.txt` selects `cpu` (default) or `d3d12`. When
`d3d12` is selected the app initializes `DflashGpuSyncEngine` and
`DflashGpuDraftEngine` at load (3.98 s) and routes RESET, SYNC, SYNC_TRIM,
TRIM and DRAFT through them; initialization failure falls back to CPU before
any sequence starts and logs requested/effective backend plus the reason.
GPUs failures after mutation invalidate the shared sequence and return an
error (the client closes; recovery reloads a clean sequence).

Evidence on app 1.0.0.42, same host, 4 cycles/4 drafts:

- CPU smoke: `f5-smoke-cpu-1.0.0.42.json` (resets 2, trims 8,
  same_output_after_reset true).
- GPU smoke: `f5-smoke-gpu-1.0.0.42.json` (identical structure, passed).
- Bench (warmup 20, 50 iterations, sync 1, drafts 4):
  CPU `f6-bench-cpu-1.0.0.42.json` DRAFT compute 131,918 us mean, SYNC 4,823 us,
  cycle RTT 143,434 us; GPU `f6-bench-gpu-1.0.0.42.json` DRAFT compute
  64,542 us (min 64,488, max 64,610), SYNC 3,490 us, cycle RTT 74,483 us.
  GPU is ~2.0x faster on DRAFT and ~1.9x on the synthetic cycle.

These are synthetic-feature RPC timings without target verification or
acceptance; the F6 real-generation campaign with the target on .57 is still
required, and the F7 optimization pass remains open.

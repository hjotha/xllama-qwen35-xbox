## Causes and measured bottleneck

Q2/Q3 kernels launched 256 threads although their CPU-compatible accumulation
needed at most 64. Reducing the group and sharing decoded weights improved the
Q3 warm DRAFT from about 110 ms to 59.75 ms while preserving tested outputs.
The reduction in overall generation time is measured in the table above.

Package .70 GPU timestamps for a short Q3 batch of five total 59.071 ms:
FFN down projection 28.4568 ms; FFN gate/up 17.1175 ms; grouped attention output
and convolution 6.7623 ms; grouped QKV/norm/RoPE 4.26594 ms. Attention itself is
0.42498 ms at this short context. In real generation, target verification adds
45.331064 ms/cycle and selector 4.904256 ms/cycle. RPC elapsed time already
includes Xbox compute and must not be added to it a second time.
[Profile](parity-gpu-70-20260928/q3-profile.json).

### Improvement 2: measured SYNC fusion

The separate and fused n7 runs produced the same 512-token output and the same
942 proposed / 368 accepted counts. Separate RPC took 49.200 ms for DRAFT plus
14.716 ms for SYNC, versus 62.682 ms for fused RPC: **1.234 ms saved per active
cycle** in this A/B. This does not demonstrate the old plan's estimated 5–7 ms.
SYNC and DRAFT still submit separate command lists and wait on separate fences.
The DRAFT engine shares the SYNC queue; there is no per-layer CPU fence in the
normal path. Removing a wait without handling buffer lifetimes and failure
recovery would be unsafe and is not part of the client fix.

### Improvement 3: root cause and correction

In greedy verification, accepting `k < n_proposed` means `draft[k]` was the first
token rejected by the target. The original pipeline predicted that same token
as the target's replacement/bonus anchor, making a match impossible. Generalizing
the old fixed `k=1` alone would not fix this. When every proposal is accepted,
the next bonus token lies beyond the available selector rows.

The corrected client chooses a different token: the selector's rank-2 candidate
along the greedy top-1 path. It selects the rejection position with the largest
`prefix_top1_probability * rank2_probability`. This score is a heuristic, not a
calibrated target acceptance probability. Only greedy requests qualify; the
existing flag remains off by default and tests explicitly set
`DFLASH_XBOX_PIPELINE=1`. A score of at least 0.25 is required, and the existing
poor-reuse guard remains in place. In the n7 tests, it stopped after 17 attempts
and four reused drafts. The second 128-token request made no new attempts;
the raw `pipeline_attempts` metric is cumulative within a server process.

Reuse still requires the expected acceptance count, position, actual anchor ID,
row count and byte size. The client checks that real target SYNC covers the
accepted prefix, then applies it before reusing proposal bytes. It avoids
chaining a new pre-draft immediately from reused output because that speculative
KV prefix has already been replaced. A missing real prefix disables remote
drafting. No such failure occurred in these tests.

The fix also drains old work without dropping a new prompt's queued SYNC and
records pipeline accept overhead separately from target verification. `begin()`
can run after prefill processing, so clearing its queue would lose real features.
The small candidate test is registered as `test-dflash-pipeline-candidate` and
passes through CTest. Hardware tests exercised real reuse, discarded predictions
and a subsequent request. They do not replace the remaining F5 fault campaign.

### Where the time goes

The fused n7 baseline's active cycle averaged **127.854 ms**:

| Component                                                          | Mean ms per active cycle |
| ------------------------------------------------------------------ | -----------------------: |
| Target verification phase                                          |                   58.212 |
| Xbox SYNC + DRAFT                                                  |                   51.518 |
| RPC outside Xbox compute, including transport/preparation/response |                   11.164 |
| Host selector                                                      |                    6.733 |
| Remaining host preparation/proposal work                           |       Approximately 0.23 |

The split run isolates approximately 45.237 ms DRAFT and 6.459 ms SYNC.
The RPC elapsed time includes Xbox compute; adding both in full would double
count it. Pipeline cycle intervals overlap and likewise must not be summed as
wall time; the throughput comparison uses completion timing instead.

Only **39.1%** of proposed tokens were accepted at n7, producing about 3.6 output
tokens per cycle including the target bonus. At this cycle cost, about 4.5
output tokens per cycle would be needed to match target-only throughput. Raising
`p_min` to 0.65 improved acceptance to 65.8% but caused 33 empty-proposal cycles:
the Xbox had already paid for the full DRAFT before the selector rejected it.
That is why this apparent acceptance improvement reduced throughput.

A fresh Q2 batch-eight GPU profile remains bit-exact against CPU: warm DRAFT
38.52–38.58 ms at its short fixture context. FFN gate/up takes 18.162 ms and
down 9.073 ms, approximately 72% of GPU timestamp time. These short-context
times must not replace the 45.237 ms DRAFT measured during generation.
[Q2 batch-eight profile](q2-n7-performance-20260928/q2-n8-profile-75.json).

The main kernel costs include serial block accumulation, group barriers and
F64-based emulation of correctly rounded FP32 FMA. Peak weight bandwidth alone
is not an adequate performance model for these shaders. Concrete next candidates
are reducing integer dependency chains in Q2/Q3 if DXIL has not already done so,
and deriving Q4 minimum corrections from Q8 block sums while preserving the
exact four-chunk FMA order. Both require measured shader changes and replay
validation; neither gain is claimed here. Reusing already-parsed SYNC buffers
would remove a duplicate copy but has no demonstrated material throughput gain.
Compacting SYNC batches is not a safe shortcut: it can change Q4 GEMM4 versus
tail-GEMV accumulation and lose the parity established above.

All matched test RPCs used real D3D12 with status 0 and mock disabled; see the
[backend proof](q2-n7-performance-20260928/backend-proof.json). The 128-token
target/sequential/pipeline outputs agree. The pre-existing 512-token difference
against target alone remains, even though corrected and original sequential
outputs agree with the corrected pipeline in the n7 comparison.

## Scope distinctions (explicit — what the observation is and is not)

1. Pre-created tmp + observer-held inode vs a write that starts with no
   prior file. The mechanism pre-creates both `*.kv.tmp` names (empty) and
   holds the fds across the ready handshake; save_state's
   `fopen(..., "wb")` (session.cpp:1589 — no pre-remove, no O_EXCL) then
   truncates THOSE inodes and its failure path (`:1609`) removes only the
   name. A production save does NOT start from a pre-existing file: the
   fresh-create branch makes the inode itself. Shared between the two: the
   bytes written, the chunked write, the fault detection, fclose and the
   remove of the name. Different: who created the inode (observer vs
   save_state) and the creation event. The measured size is a property of
   the write/failure path, obtained through an inode lifecycle that a cold
   production save does not use; the observation mechanism, not the write,
   is what pre-creates the file.
2. Observed file size != fsync/durability. The capture is `fstat` size on
   the held inode: it proves the bytes went through libc into the file
   (address space / page cache), not that they reached durable media.
   Neither this test nor production `save_state` calls
   fsync/fdatasync/FlushFileBuffers (grep over src/bridge/session.cpp and
   src/bridge/*.cpp: none). Production atomicity claims in this plan are
   namespace atomicity (tmp+rename) under process failure — NOT power-loss
   durability of file contents. No fsync or durability claim is made here.
3. Simulated I/O failure != process death, != concurrency, != Xbox handler.
   RLIMIT_FSIZE makes the kernel reject the write beyond L: a clean
   in-process I/O error following the real failure path. It does NOT kill
   the process mid-write (SIGXFSZ explicitly ignored; the process-death
   variant stays structurally covered only — loader reads the final path,
   B11, prune). It exercises a single-threaded save with no concurrent
   saver (device-side slot concurrency is a separate, already-passed gate:
   T2b 4/4 on device — not demonstrated by this host test). It contains no
   network code (grep http|socket|connect over the run logs: 0), so the
   Xbox API handler's behavior for a mid-write I/O failure is NOT
   exercised here — only F1/F2/T16 (open, rename, pre-write rejections)
   ran on the device; a mid-write I/O failure on the device remains part
   of the open device-side gap until the probe (if approved) runs there.

## Findings (measured, not reasoned)

1. Full rebuild from v2 contents WORKED IN THE TESTED CASES:
   kv_before=42, pf=tail, drafted/acceptance identical to control in
   aggregate (4/3; longgen 29/34), text identical. This shows same greedy
   outputs + same aggregate draft behavior on these prompts — NOT full
   state equivalence (see scope note above).
2. NO latency win IN THE TESTED HARVEST-BASED METHODS: harvest runs at
   prefill rate (418.6ms/42tok ≈ 10.0ms/tok vs control 677ms/62tok ≈
   10.9ms/tok). Totals: full 725ms vs control 685ms (short). This does
   NOT conclude universal impossibility — it covers the harvest family
   only (both arms hide a forward pass over kept tokens). A harvest-free
   method (M3 zero-carry) remains untested; see T2/M3.
3. Bare carry did NOT fail ON THESE PROMPTS (correction of the earlier
   analysis, still bounded): 88% acceptance ≈ full 85%, text identical
   on a short + a 64-token completion referencing recent context. This
   does NOT demonstrate general validity — open: prompts requiring
   deep-prefix discrimination, longer generations, divergent tails.
   Cost floor identical here (harvest of the last row still required).
4. Quantified but NOT adopted (rejected: MTP must stay on): classic
   first turn after restore (tail prefill only, no harvest) ≈ 258ms vs
   685ms — 2.6x. Recorded for the v3 prize calculus only.
5. v3 prize — PROJECTION, not a measurement (from measured components):
   IF mirror-blob restore costs ≈ blob restore (~8ms + small constant,
   UNVALIDATED) then restore ~10ms + tail-only prefill with drafting from
   turn start ≈ 260ms vs 685ms today, i.e. ~425ms per post-restore
   continuation at this size. Treat as estimate for the authorization
   decision, not as evidence.
6. Memory: no new persistent allocation; transient h_rows = n*n_embd*4B
   (<0.5MB here; 21MB worst case at n_ctx=2048 — must be chunked/freed,
   as implemented). Scratch KV copy avoided (seq-0 harvest + re-set).

## Structural impediment (reproducible)

- n_seq_max=1 (default; part of the state fingerprint) forbids a scratch
  sequence — verified in code (session.cpp:434,526,1385), so the harvest
  must reuse seq 0 (clear -> harvest -> set_data).
- llama_decode append-only over occupied rows (re-confirmed: the harvest
  MUST clear first; re-decode over the restored rows is not attempted).
- Evidence: per-arm JSONs + slice.log under slots-rev211/T1 and
  slots-rev211/T1-longgen (T1 lines, turn lines, prefill/drafted lines).
